# Privacy and diagnostics

TiPlay's product flow uses local authentication and a direct USB/Wi-Fi connection to the iPhone. No account, remote authentication service or automatic diagnostic upload is used. The iPhone's CarPlay apps have their own internet and privacy behavior.

The Android phone stores app preferences, paired-device selections, pairing data and bounded diagnostic logs in app storage. Authentication and pairing material are kept out of Android backup. Uninstalling removes app-private data; exported reports in Downloads remain until you delete them.

Diagnostic export is initiated by you. Reports include app/device versions, display settings and negotiation, connection transitions, Wi-Fi band/channel and state, and decoder recovery events. The exporter filters protocol payloads, credential-bearing lines and common identifiers. Redaction cannot promise to recognize every vendor-specific string: review reports before posting them publicly. A GitHub issue is public.

When the document picker or Downloads storage is unavailable, reports save under `Android/data/<package>/files/diagnostic-reports/` on primary external storage without requesting storage permission. The confirmation shows the actual TXT file path. The release package is `com.ujzk.tiplay`; debug builds use `com.ujzk.tiplay.hudtest`. File managers on newer Android versions may restrict access to `Android/data`; use **View** or **Share** in TiPlay instead. If external storage is also unavailable, reports save in private app storage. Each fallback location retains its newest eight exports, and uninstalling removes them. Sharing grants read access to the selected report only; nothing is sent automatically. On Android 9 and older, other apps with storage permission may be able to read the external reports.

The phone + browser profile plays enabled CarPlay audio in the browser without microphone demand. When the iPhone requests Siri or call microphone input, Android routes speech, navigation and capture through verified car HFP/SCO Bluetooth while music and other audio outside that mix continue in the browser. Android requests microphone permission while connecting in the foreground when CarPlay sound is enabled; capture opens only for that demand. Permission denial still permits playback, and there is no handset or browser microphone fallback. The browser never requests microphone permission or opens capture tracks. Advanced settings can disable CarPlay audio and leave sound and calls on the iPhone-to-car Bluetooth connection. See [audio and microphone routing](TESLA_BROWSER.md#audio-and-microphone) for routing, release and vehicle-validation limits.

CarPlay encoded video goes directly to the browser without creating an Android video decoder or local video surface. Ordinary AirPlay mirroring also forwards encoded video to the browser, but its companion AAC-ELD audio is decoded on Android. AirPlay URL video and audio are browser-decoded; still photos use an Android Surface/encoder bridge. URL playback can fetch resources from the iPhone or the sender's media service through Android's authenticated proxy or supported direct resource URLs; those services have their own network and privacy behavior. Bluetooth/Nearby devices, Wi-Fi/Location and platform-required local network permissions support discovery and transport. Local VPN permission supports the USB link or the optional hotspot address repair; it does not provide a remote internet VPN. Address-repair VPN cannot replace another VPN, including the USB-link VPN.

The retained DiLink 5.1 head-unit cluster profile optionally uses Android Usage Access to follow theme and mini-map-card visibility. This is upstream compatibility code, hidden from the phone + browser product. This permission exposes app-activity history. The retained implementation filters the results to four stock BYD cluster activities, processes them locally, and logs only inferred cluster theme/visibility changes. Unrelated activity events are not retained or uploaded. Automatic mode is opt-in; disabling it stops these queries. Usage Access can also be revoked as described in [BYD navigation](BYD_NAVIGATION.md#dilink-51-theme-profile).

The browser page stores the pairing code and phone address in browser storage and removes the code from the link fragment after opening. The fragment is not sent to the static host; the endpoint in the `?t=` query is sent to that host. Authenticated requests send the code to the phone over HTTP. Video, audio, proxied AirPlay resources and controls are not encrypted by TiPlay on the local network; use a secured hotspot or existing Wi-Fi network. An open network provides no Wi-Fi encryption. **New code** invalidates the old code and ends the current browser session. Changing Android's address or port preserves the code but requires a manual browser address update or a new pairing link; the phone does not send an endpoint-migration notification.

The static website has no analytics script or account. GitHub Pages and GitHub apply their own policies when you use those services.
