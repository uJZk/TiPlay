## 五秒窗口

- 只统计新解码帧的 canvas 绘制提交；调整尺寸或 WebGL 恢复时重画旧帧不计入。
- FPS：按帧间隔排序，去除最快与最慢各 5% 后，以 `1000 / 平均帧间隔毫秒` 得到中间 90% 的
  平均 FPS；最长间隔的 5% 得到最慢 5% 的平均 FPS。不是对瞬时 FPS 做算术平均。
- 延迟：按延迟排序，中间 90% 去除两端各 5%；最差 5% 取最高延迟尾部，单位毫秒。
- 窗口按呈现采样时间滚动，样本满五秒即移出；边界按比例加权，启动期间使用已有样本。
  无样本显示 `—`。断流和配置 epoch 切换清空统计。

## 延迟起点与时钟

用户选择 iPhone 采集 → 浏览器呈现，不能拿安卓收到帧的时刻替代起点。
实现使用 iPhone 视频头的原始 NTP 32.32 帧时间戳，借助已有 AirPlay 双向 timing 交换，
映射到安卓 `System.nanoTime()`。未完成同步，或十秒未收到有效 timing 响应时，不提供帧时间。

网页通过 `/hello` 扩展的 `clockMs` 对齐安卓与浏览器的单调时间。初次请求提供样本；
之后每五秒连续测三次，选择往返耗时最小的样本。往返超过一秒的样本拒绝；网页同步样本
十五秒后过期。跨 Worker 使用 `performance.timeOrigin + performance.now()`，避免计时起点不同。

`GET /video?…&timing=1` 可选请求 kind 5 记录：沿用协议 v1 的 24 字节头，通过 epoch、帧时间
匹配后续帧；负载为 little-endian float64 的安卓单调时间毫秒。时序记录与视频记录放入
同一个输出缓冲区，一次写出。NAL 数据、原视频帧头与旧客户端协议不改变。
不请求 timing 的旧客户端仍只收到既有记录；新网页连接旧 App 时延迟显示 `—`。

不同步、时间戳在未来或延迟超过十秒的样本均拒绝，不用到达时间补造延迟。
HTTP 同步采用往返中点估算，单程网络不对称会引入误差；`clockRttMs` 保留在完整诊断里。

### 尚需实机确认

目前测到的是“同步后的 iPhone 帧时间戳 → 浏览器 canvas 绘制提交”的估计值。
本轮尚未进行真实设备上的采集到屏幕延迟测量，不能宣称已验证严格的采集到物理屏幕延迟：

1. 视频头时间戳需要确认代表采集时刻，还是计划呈现时刻；只验证连续帧间隔不足以确定语义。
2. 浏览器绘制提交不等于屏幕扫描出光，尚未包括可验证的合成、显示扫描延迟。

## 删除的降级路径

删除本项目的 `site/play/mse.js`、`fmp4.js`、相关独立测试、golden fixture 中的 MSE 专项断言，
以及 `<video>` DOM、专用样式、MSE 能力探测、App 分支和离线缓存资源。
保留用于 WebCodecs 的协议 golden fixture 检查与 Worker／主线程、WebGL／2D 路径。
站点与安卓 HTTP 网页的 CSP 改为 `media-src 'none'`；缓存更新到 v12。

非 loopback 的 HTTP 地址不再支持视频播放，页面提示使用支持 WebCodecs 的安全上下文。
用户明确指出特斯拉在 D 档会暂停 `<video>`：这是播放路径选择的产品约束，不能仅以浏览器
能否解码来判断是否可用。依赖 `<video>` 的 MSE 降级路径因此移除，特斯拉路径保留
WebCodecs + canvas。用户已确认这条保留路径在特斯拉 D 档实测正常；此为用户提供的
实测结果，不再列为待验证项。浏览器支持 HTML `<video>` 不代表它适用于本产品。
汽车浏览器使用 HTTPS 网页；安卓自身 `localhost` HTTP 网页仍是安全上下文。
上游类、包名和既有回调保留，新时钟钩子有默认实现，便于复用后续上游更新。
