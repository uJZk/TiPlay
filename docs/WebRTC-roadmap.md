## 约束摘要

- 只覆盖安卓手机 + 车浏览器，不包含原生车机。
- 永不二次编码。允许解密、配置解析、访问单元整理及传输封装，保留源压缩视频。
- 媒体只走局域网，不引入公网或 TURN 中转。GitHub Pages 可托管 HTTPS 静态页，
  但静态托管不等于信令或安卓可达；配对须绑定真实设备、会话和 DTLS 指纹。
- 采用可靠有序 DataChannel，不配置 `maxRetransmits` 或 `maxPacketLifeTime`。
  完整压缩接收和依赖解码继续；触控追赶允许跳过已解码旧画面。
- 视频、音频各自相对源呈现时间不超过 +300 ms，通常尽量低；不是固定缓冲目标。
  触控只追赶视频，不重置、加速或改变音频时间线。详见交接契约的测量边界。
- 回声、麦克风和通话继续走既有安卓 HFP/SCO，不另建浏览器采麦或 AEC 方案。
- 保留现有配对、浏览器会话所有权、触控及独立音频语义；车端不依赖复制粘贴。
- 完整原始视频只保存一份，下游事件引用原记录；不静默采样或遗漏原始码流。

### TCP 背压实测

[Debug TCP 接收探针](Diagnostics.md#debug-tcp-receive-backpressure-probe)
的持续运动测试结果：

| 阶段 | 安卓接收情况 | 到达时间减源计划呈现时间 |
| --- | --- | --- |
| 无限制基线 | 约 11–12 Mbps、60 fps | 通常约 −60 至 −70 ms |
| 70% 读取预算 | 约 7.2 Mbps | 增长到约 4.5 s |
| 40% 读取预算 | 约 4.1 Mbps，帧率进一步降低 | 最大约 8.18 s |
| 恢复无限制 | 短时约 41.32 Mbps、107 fps，随后回到基线 | 快速回到约 −66 ms |

读取限速生效但产生明显积压；吞吐下降不等于源编码降码率。源端是否减少
生成或丢弃帧仍未确定。负偏差表示相对计划呈现时间提前，不是负采集延迟。

此次测试所用的原 HTTP 浏览器会丢弃超过呈现期限的帧并保留上一幅 Canvas 画面，
秒级积压与冻结观察相符；缺少该次浏览器计数，冻结位置尚未确认。测试版
DataChannel 对压缩队列超载/超时明确结束并恢复会话，避免隐瞒压缩数据缺口后继续
播放；仅允许跳过已解码的旧画面。这些策略仍须验证真实网络与解码负载。
不通过数秒播放窗口掩盖积压；缩小接收缓冲区也只能作为独立实验。

## 阶段 2：可靠有序 DataChannel 已实现，跨设备服务能力待验

[产品协议与资源边界](CarPlay-DataChannel.md#native-and-browser-transport) 已实现：
安卓固定 `io.github.webrtc-sdk:android:150.7871.01`，包含四种 ABI，并记录许可证、
来源、线程和生命周期处理。三个可靠有序通道分别承载视频、音频与控制，不使用
原生音视频轨，不设置部分可靠性参数，也不引入公网 STUN/TURN 或媒体中转。

源记录保留原线格式、epoch、序号与时间信息，在最多 16 KiB 的完整消息内分片，
再由网页按有序通道完整重组；协商的 SCTP 上限进一步限制片段。会话身份、
长度、偏移和连续性均检查后再分配/消费。应用层信用和累计完整记录确认配合
`bufferedAmount` 限制在途工作；后者不能证明远端消费、解码或呈现。

媒体与控制保持逻辑分离，但多个通道共享 SCTP 关联和拥塞资源。安卓视频和音频
可靠队列都限定 200 ms 最老媒体年龄，并分别限制字节数、帧/记录数；超载、
超时或长时间消费停滞明确结束会话，不丢压缩预测帧后继续，也不无界排队。
完整 AU、重组、信用、异常长度及队列失败已有软件测试；实际热点上的大 IDR、
丢包重传、控制响应、持续吞吐与热负载仍须用真实 iPhone/安卓/车端测量。

原始视频仍只保存一份源 TCP 采集，下游通过会话、记录 ID 和字节范围关联，
明确解密及 Annex-B 整理过程；写盘失败暴露完整性边界，不宣称未知范围已保存。
D 使用的原生视频轨保留为实验结果，不替换产品的源压缩 DataChannel 路线。

## 阶段 3：时钟、独立音频与触控追赶已接入，物理输出待验

`ScreenCodec.senderNanos` 读取源呈现时间，`NtpClock` 在同步有效时映射到安卓
单调时钟；测试版复用该映射并通过控制通道校准安卓与浏览器时钟。源锚点缺失时
明确报告本地/到达时刻测量边界，不把首帧到达当作源呈现零点或宣称满足
源相对时延。计时映射和软件提交指标不能替代实际面板与声学输出测量。

AAC、Opus、LPCM 保留源格式和独立语义，由网页独立解码/输出，不为适配
WebRTC 二次编码。触控接入独立控制通道，视频以连续游标平滑选择已解码图像
追赶，音频保持原时间线。初始追赶参数为最高 1.5 倍、速度变化率 4/s；
重复触控保持连续，松手不恢复旧积压。这些是测试参数，不是实车平滑性证明。
解码准入保留必要预测前视，并限制待解码工作与已解码图像；不能只允许一个
压缩 AU 等待输出而造成依赖死锁。实际硬件内部队列及编解码配置仍需实测。

WebRTC 反馈影响安卓调度，不会自动改变 iPhone 编码器。现有接入层有请求
关键帧操作，未确认运行时源码率控制命令。持续超载无法同时保证完整输入、
有限资源和时延上限；须报告违约并走真实支持的协商/恢复边界，不能通过
暗丢压缩预测帧、重置 PTS 或无界积压使指标看似通过。

## 阶段 4：真实 CarPlay 验收与切换

比较真实 iPhone → 安卓 → 特斯拉的基线与候选方案，验证网页硬件解码、
独立源相对 +300 ms 音视频上限、触控平滑追赶和一份完整原始视频记录。
覆盖大 AU、重传、持续运动、热负载、档位切换、后台恢复、热点重启、
浏览器接管、存储压力及 HFP/SCO 路由；物理显示和声学时延须有独立测量。

D 的单机可播放已作为前置证据记录；DataChannel、认证配对、媒体与触控的软件
实现已接入测试版。beta.2 有真实 CarPlay 播放反馈，beta.3 有电脑 host↔host UDP 证据；
车机选中候选、源压缩媒体实际硬解、持续真实 CarPlay、
档位切换及端到端物理输出验收仍未完成。测试版部署在独立 `/webrtc/` 路径，
正式站点根目录保持迁移前行为；只有实车验收通过后才决定正式默认传输切换。
