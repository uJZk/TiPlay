# WebRTC 实施路线图

## 当前决策与下一步

产品实施路线遵循 [CarPlay 可靠有序 DataChannel 交接契约](CarPlay-DataChannel.md)：
安卓传递完整压缩媒体，车端网页控制硬件解码和 Canvas 输出，音频保持独立时间线。
本页只维护本次实验的证据、进度和实施顺序；具体协议、时延及资源要求以交接契约为准。
现有 HTTP → WebCodecs → Canvas 仍是正式运行基线，尚未接入 DataChannel 媒体链路。

**用户最新确认：D 可以播放。** D 是同一车浏览器内的本机 WebRTC 接收视频轨
→ MediaStreamTrackProcessor → VideoFrame → Canvas 合成源测试。它已经有
实车可播放的用户观察，不能再把此前笼统的“P 档视频不能播放”套用到 D。

尚未收到明确的 P → 非 P → P 连续播放结果、具体编码、主线程/Worker 路径、
浏览器/车辆固件和统计导出，因此这些项目仍待验证。D 可播放不证明安卓到
车端 UDP 已连通，也不证明真实 CarPlay、硬件解码或物理时延已通过。

**下一实施重点：验证 `169.254.111.111` 上的真实 UDP/ICE 路径，随后建立最小
可靠有序 DataChannel 传输。** 换挡持续播放和网页实际硬件解码验证并行补齐；
D 的结果不更改已选产品传输方案。

## 约束摘要

- 只覆盖安卓手机 + 车浏览器，不包含原生车机。
- 永不二次编码。允许解密、配置解析、访问单元整理及传输封装，保留源压缩视频。
- 媒体只走局域网，不引入公网或 TURN 中转。GitHub Pages 可托管 HTTPS 静态页，
  但静态托管不等于信令或安卓可达；配对须绑定真实设备、会话和 DTLS 指纹。
- 采用可靠有序 DataChannel，不配置 `maxRetransmits` 或 `maxPacketLifeTime`。
  完整压缩接收和依赖解码继续；触控追赶允许跳过已解码旧画面。
- 视频、音频各自相对源呈现时间不超过 +300 ms，通常尽量低；不是固定缓冲目标。
  触控只追赶视频，不重置、加速或改变音频时间线。详见交接契约的测量边界。
- 回声、麦克风和通话继续走既有安卓 HFP/SCO，不另建浏览器采麦或 AEC 方案。
- 保留现有配对、浏览器会话所有权、触控及独立音频语义；车端不依赖复制粘贴。
- 完整原始视频只保存一份，下游事件引用原记录；不静默采样或遗漏原始码流。

## 当前证据与边界

| 项目 | 当前观察 | 尚未证明 |
| --- | --- | --- |
| D 本机 WebRTC → Processor → Canvas | 用户明确反馈“D 可以” | 跨设备网络、换挡持续播放、实际硬件解码、真实 CarPlay 通过 |
| 其他播放路径 | 此前反馈“P 档是视频不能播放”，未明确指向 B/C；D 现已单独确认为可播放 | B、C 的具体失败原因和档位对照 |
| 手机到车端连接 | 曾出现 ICE 收集超时及局域网连接失败 | 该路径已连通；手机本地动画只证明生成了测试源 |
| 本地权限弹窗 | 用户未看到弹窗 | 不能单凭这一点判断权限；接收视频本身不要求摄像头或麦克风授权 |
| 热点地址 | 用户用 Shizuku，正常 TiPlay 地址为 `169.254.111.111` | HTTP/TCP 可达不等于 UDP 可达 |
| ICE 地址别名实验 | 额外公布附加地址候选，保留原候选及 UDP 端口 | 候选生成不会创建或重新绑定套接字，尚无该地址实车双向连通证据 |
| TCP 接收背压 | 持续运动测试中呈现偏差增长，用户同时报告网页冻结 | 源编码码率是否适应仍未确定；当前读取限速不作为默认拥塞闭环 |

Shizuku 在热点接口添加真实 `/32` 地址，见 [热点地址说明](Hotspot-address.md)。
页面可筛选或交换候选，不能强制浏览器绑定指定网卡。实际 UDP 端点须能
在该地址接收和回包；单向到达也不足以通过 ICE。

### TCP 背压实测

[Debug TCP 接收探针](Diagnostics.md#debug-tcp-receive-backpressure-probe)
的持续运动测试结果：

| 阶段 | 安卓接收情况 | 到达时间减源计划呈现时间 |
| --- | --- | --- |
| 无限制基线 | 约 11–12 Mbps、60 fps | 通常约 −60 至 −70 ms |
| 70% 读取预算 | 约 7.2 Mbps | 增长到约 4.5 s |
| 40% 读取预算 | 约 4.1 Mbps，帧率进一步降低 | 最大约 8.18 s |
| 恢复无限制 | 短时约 41.32 Mbps、107 fps，随后回到基线 | 快速回到约 −66 ms |

读取限速生效但产生明显积压；吞吐下降不等于源编码降码率。源端是否减少
生成或丢弃帧仍未确定。负偏差表示相对计划呈现时间提前，不是负采集延迟。

现有浏览器会丢弃超过呈现期限的帧并保留上一幅 Canvas 画面，秒级积压与
冻结观察相符；缺少该次浏览器计数，冻结位置尚未确认。未来 DataChannel
不得直接照搬此压缩帧丢弃策略，须遵守完整压缩接收与解码的交接契约。
不通过数秒播放窗口掩盖积压；缩小接收缓冲区也只能作为独立实验。

## 阶段 0：补齐车端播放证据

[车端单机测试页](https://tiplay-webrtc-probe.sunlitbloom10.chatgpt.site/gear.html)
排除了手机配对和跨设备网络依赖，四项分别观察：

| 项目 | 观察内容 | 状态 |
| --- | --- | --- |
| A：纯 Canvas 动画 | 页面计时和绘制；不证明视频能力 | 仅作对照 |
| B：普通 H.264 `video` | P 档起播、暂停和换挡行为 | 待明确单项结果 |
| C：H.264 WebCodecs → Canvas | 送入、解码、绘制计数和实际硬件使用 | 待明确单项结果及硬件证据 |
| D：本机 WebRTC → Processor → Canvas | 本机 ICE、接收视频轨与绘制 | 用户确认可播放；换挡对照及运行配置待补 |

B 的短片先下载到 Blob，C 使用同源 H.264 数据。D 使用同页两个
PeerConnection，属于真正的本机视频轨测试，不是手机到车端的网络测试。
页面不自动恢复暂停，也不读取车辆档位。

记录浏览器/车辆固件、页面版本、编码、处理路径和统计。按同一路径比较
P → 非 P → P 的画面及计数，区分页面、网络、解码与绘制停止。D 成功不能
替代 C 的硬件解码证明；`prefer-hardware`、低 CPU 或配置成功也不能单独证明。

## 阶段 1：真实 UDP/ICE 和认证信令

1. 在运行 TiPlay 的同一台安卓手机上确认热点及 Shizuku 附加地址有效。
   [浏览器配对实验页](https://tiplay-webrtc-probe.sunlitbloom10.chatgpt.site/)
   的 Cloudflare 信令只用于实验，不属于产品纯局域网信令。
2. 对照原候选和别名实验，记录所选候选对、协议、双向收发及恢复。
   如浏览器套接字不能复用附加地址，改用安卓原生 UDP/ICE 最小探针，
   验证真实绑定、回包源地址、库的链路本地地址枚举及端口控制能力。
3. 定义认证配对和 DTLS 指纹绑定，保留代码失效、接管、断开和 epoch 退役语义。
   HTTPS 页与 DTLS 加密不能单独证明信令身份绑定可信。
4. 验证热点重启、地址重加和重连。通过条件是实际地址上的双向 ICE 连通，
   不是 HTTP 成功、信令成功、候选已添加或手机本地动画。

## 阶段 2：可靠有序 DataChannel 最小实现

依 [交接契约](CarPlay-DataChannel.md#datachannel-deployment-and-protocol-work)
选定并固定安卓 WebRTC 依赖，验证 ABI、生命周期、线程和许可证。
实现完整 AU 分片与重组、会话/流/epoch 标识、原时间基、配置身份、
应用层信用与有限资源核算；`bufferedAmount` 不代表远端消费或呈现。

媒体与控制逻辑分离，保留控制优先调度；多个通道仍可能共享 SCTP 拥塞和
队头阻塞。选择分片大小须考虑 `maxMessageSize` 和消息交织能力，不把
大 IDR 作为长期独占关联的单条消息。首次目标是有限资源下完整、可观测的
压缩传输，再接入网页硬件解码。原生视频轨仍保留为实验结果，不替换该路线。

## 阶段 3：时钟、独立音频与触控追赶

现有 `ScreenCodec.senderNanos` 读取源呈现时间，`NtpClock` 在同步有效时映射
到安卓单调时钟。验证语义并沿用可用锚点，继续映射到浏览器输出；无有效
锚点时明确测量边界，不把首帧到达当作源时间零点或宣称满足源相对时延。

AAC、Opus、LPCM 保留源格式和独立语义；音频解码位置与线格式按交接契约
选型，不能为适配 WebRTC 二次编码。触控立即转发，视频平滑选择已解码图像
以追赶，音频保持原时间线。参数集、预测依赖、必要解码前视和有限硬件队列
必须真实满足，不能只允许一个压缩 AU 等待输出而造成依赖死锁。

WebRTC 反馈影响安卓调度，不会自动改变 iPhone 编码器。现有接入层有请求
关键帧操作，未确认运行时源码率控制命令。持续超载无法同时保证完整输入、
有限资源和时延上限；须报告违约并走真实支持的协商/恢复边界，不能通过
暗丢压缩预测帧、重置 PTS 或无界积压使指标看似通过。

## 阶段 4：真实 CarPlay 验收与切换

比较真实 iPhone → 安卓 → 特斯拉的基线与候选方案，验证网页硬件解码、
独立源相对 +300 ms 音视频上限、触控平滑追赶和一份完整原始视频记录。
覆盖大 AU、重传、持续运动、热负载、档位切换、后台恢复、热点重启、
浏览器接管、存储压力及 HFP/SCO 路由；物理显示和声学时延须有独立测量。

D 的单机可播放已作为前置证据记录，跨设备可达、DataChannel 实现、真实
CarPlay 和端到端验收仍未完成。只有这些条件通过后才切换正式默认传输。
