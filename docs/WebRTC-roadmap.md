# WebRTC 实施路线图

## 当前实现与验证边界

正式网页媒体入口已改为可靠有序 WebRTC DataChannel，不再静默回退到 HTTP
媒体流。安卓正式产品关闭旧 `/video`、`/audio` 入口，旧缓存网页不在验收范围。
HTTP 只保留 SRP 配对、公开发现和随机 bearer 资源读取/退出；控制只走已认证 DataChannel。安卓只做接收、解密、配置/AU 整理和分片，车端网页复用 WebCodecs
与 Canvas；视频永不二次编码。AirPlay 镜像与普通音频复用同一传输，URL
投屏保留资源读取/解复用路径，使用共享投屏播放策略。

协议、资源和信任边界见 [DataChannel 契约](CarPlay-DataChannel.md)。当前代码
不等于已发布 APK，也不等于实车验收通过。先前 **D 可以播放** 是同一车浏览器内 WebRTC 接收视频轨 → Processor → VideoFrame → Canvas
的本机合成源证据。它不能替代实际硬解、换挡持续播放或物理时延测量。此前 beta.2/v70 已有
用户确认的真实 CarPlay 播放，beta.3/v71 已记录电脑 host↔host UDP；这些旧版
观察仍不代表当前整合版已通过设备验收。正式页面覆盖
<https://ujzk.github.io/TiPlay/>，删除独立 `/webrtc/` 子站，不留别名或重定向；
APK 默认使用正式根页。已发布 APK 为 0.2.20-beta.14/code56，正式根页另已部署 v81；
APK 与网页构建来源和独立核验见
[构建记录](Build.md#beta-release)。v74 修复了控制排队阻塞媒体、
诊断上报放大，以及 URL 音频裁剪、分段调度和重采样接缝；现场证据与验证边界见
[诊断](Diagnostics.md#airplay-url-playback-evidence)和[测试](Testing.md#webrtc-integrated-acceptance)。

浏览器音频方案继续保留。CarPlay／镜像已经使用持续 AudioWorklet 输出、有界
PCM 队列、跨包 Soxr 状态和欠载恢复，并非尚未实现这些机制；当前 DSP 是
wasm2js 生成的 JavaScript，不是运行时 WASM。主线程 `currentTime` 分批刷新是
已确认的观测边界，不能据此认定整个音频时钟或物理 DAC 错误。
URL 投屏仍是独立的 Canvas／Web Audio 引擎，以 `AudioBufferSourceNode`
分段输出，由页面 rAF 补充最多 500 ms、且受共同音画覆盖限制的排程；它没有
复用直播 Worklet。WebCodecs 的实际解码由浏览器异步实现，不能将页面上的
解复用、PCM 处理及排程概括成全部解码算法都在主线程。

下一步先在 Cloudflare Workers 部署当前 wasm2js 与真正 WASM 的同源 PCM
对照页，并直接上传有界结果；此项尚未开始，本轮不实现测试页或迁移音轨。
独立设计分析建议让实时输出持续消费样本，将网络／重计算与实时回调分离，
避免播放热路径分配及阻塞；这些原则不是已完成的优化或消除爆音的证明。
原生 WebRTC 音轨保留为 CarPlay／镜像等非 URL 场景的备选，须另行核验安卓
解码／混音、音画同步和输出延迟；URL 不能自动随之迁移。执行范围见
[待办对照实验](Todo.md#cloudflare-workers-audio-comparison)。

## 四场景播放策略

所有模式从 `site/play/delay-plan.js` 的共享 profile 取参数，复用时钟、有限
解码准入、呈现队列和错误恢复。参数是实现初始值，尚未做实车性能调优证明。

| 场景 | 优先级 | 已实现策略 |
| --- | --- | --- |
| CarPlay 触控 | 延迟略优先于流畅 | 触控立即转发；只推进视频游标，quintic 平滑追赶最高 1.25x；750 ms 活动保持；重复 move 不重启；松手不回填旧积压 |
| CarPlay 非触控 | 流畅优先于延迟 | readiness +20 ms 抖动余量、缓慢减少视频等待，独立源相对 300 ms 上限 |
| AirPlay 镜像 | 流畅略优先于延迟 | readiness +30 ms 余量、40 ms 初始计划；独立源相对 300 ms 上限；遵循 iOS 镜像暂停信号，继续完整解码而不提交画面 |
| AirPlay 投屏 | 流畅远优先于延迟 | 以音频领先的媒体时钟预缓冲：启动 750 ms / 恢复 1500 ms；时间、帧数和 GPU 字节共同有界，资源满或短片结束时不因水位死锁 |

CarPlay/镜像的 300 ms 是独立音视频上限，不是固定缓冲，也不再使用旧的
音频相对视频 −45/+125 ms 窗口。触控不能重置、加速或改变音频时间线。
无可信源时钟锚点时保留 unknown，首帧到达不冒充源时间零点。投屏使用
接收端媒体时间，不把直播源相对 300 ms 限制套在 URL 预取上。
音频输出检查包含现有可观测的安卓/浏览器、设备和滤波误差；上游 iPhone
NTP 锚点不确定度尚未在线格式中单独传递，`within-bound` 只表示当前软件
映射下的已知边界，不能证明物理源相对时延。

### 参数核验与调优边界

参数核验同时检查实际调用、边界回归和捕获中的有效窗口。通过单元测试只能
证明软件约束与恢复分支，不能把经验初值写成已经实车最优。

| 参数 | 核验结论 |
| --- | --- |
| 直播 300 ms、提交余量 20 ms | 目标最大为 280 ms，提交预算只预留一次；这是软件源时序约束，缺锚点时不能认证达标。 |
| 直播音频 300−U−30 ms | U 包括已知时钟／输出／滤波及实际外推距离的速率误差；通常媒体计划和语音首次准入保留 30 ms。语音已实际输出后的恢复使用 300−U 实余量，20 ms 等待每次恢复只计算一次，真实重采样预热跨回调保留。播放中 U 波动不冒充网络计划改变，实际输出仍逐段按完整 U 检查 300 ms 源龄；不重复加算输出延迟。尚缺上游 iPhone 锚点误差和物理扬声器测量。 |
| 非触控 +20 ms、镜像 +30 ms／初始 40 ms | 属于经验初值。目标增加以 0.02 的延迟变化率积累，对应约 0.98x 播放；增加 80 ms 约需 4 秒，另有 85 ms 计划提前量。目标值不等于当前实际缓冲。 |
| 触控 750 ms 保持、最高 1.25x | 保持时间是交互经验值；平滑曲线的导数经 1.875 系数修正以约束追赶速度。触控 profile 的 8 ms 余量实际不参与强制为零的目标公式。 |
| 24 帧／64 MiB 与投屏 32 帧／256 MiB | CarPlay／镜像保持 64 MiB；投屏按用户要求从 96 调至 256 MiB，仍限制 32 个排队画面，保留画面另计入字节。均按编码尺寸 RGBA8 估算，不等于厂商池或真实 GPU 总量。4K30 约八帧／267 ms，1080p30 受共同帧／字节限制约一秒；待实车标定，扩容不能解决持续吞吐不足或更小私有池。 |
| 投屏 750／1500 ms、视频前瞻 2 s、音频前瞻 3 s | 水位按播放速率换算为媒体秒，容量、私有解码池和短片结束可提前启动。旧 beta.12 的 96 MiB 在 1080p30／1440p30 约覆盖 400／200 ms；当前 256 MiB 同样受帧数／私有池约束，4K30 仍约 267 ms，不能保证完整水位。 |
| 投屏音频最多排程 500 ms | 实际还受共同可播放末端限制，有限视频池下可明显更短。迟调度不得将多个欠期片段同时启动，也不应无条件触发完整恢复水位。 |
| CarPlay buffered music 2 s 前送、400 ms 锚点 | 前送量、保留队列和实际播放目标不同。现场约 2.2 s 队列仍发生时钟恢复，不能据此继续加大缓冲；10 ms 读取请求也不保证已有 10 ms 启动水位。 |
| device fit ±20000 ppm、phase ±1000 ppm | 分别约束设备拟合与额外相位校正，不是同一个总重采样上限。现场设备拟合约 −12500 ppm 未越范围，但新拟合拒绝后会沿用旧值；须结合真实接受年龄／拒绝原因，不能认证为物理晶振偏差。 |
| 输出参考 750 ms、外推 1000 ms、device fit 4／16 s | 拟合至少需要 4 s、历史保留 16 s；新鲜原生拟合优先，否则用独立渲染进度，统一渐变已应用速率。确认超过 1000 ms 的观察空窗仍保留名义速率重置／重学。原生保留 40 ms 相位门槛；渲染速率候选须经 worklet token 确认属于同一实际样本代次，再进入长窗拟合，不因主线程读数分批推进清空历史，也不以证明到达时间延长原始候选新鲜度。矛盾输出仍需两个新鲜前进点确认。渲染进度不能单独证明物理设备速率。 |
| source fit ±1000 ppm、30／120 s | 至少 30 s 的源样本跨度才拟合，历史保留 120 s；到达抖动不能直接解释成采样晶振偏差。设备和源的精确合法边界要避免减法或倒数的浮点误拒，真正越界仍须拒绝；这是软件接受范围，不是已测得的晶振极限。 |
| device／source MAD 3／0.5／1.5 ms、source 1 s 桶、device／source 2／10 s 配对 | 原生 device MAD 保持 3 ms；渲染拟合另计已观测最大量子的半宽，原始 MAD 与接受不确定度分开。等号、阈值两侧、拒绝后的接受年龄均有回归；较大渲染块的首次 4 s 拟合可能明显偏离，不能视为高精度测量。这只证明软件门槛，不证明实车最优。 |
| 计划历史 125 ms、提前 85 ms | 独立完整激活日志验证历史裁剪、截止反解及音频独立；被新计划覆盖的同刻／未来激活先移除，10,000 次同刻突发不再膨胀成递归溢出。参数保持不变。 |
| PCM 半采样与 8 ULP 保护 | 用于样本格点及浮点舍入；音频 EOF 使用样本格点和实际音频时钟，不再复用视频 2 ms 容差。1x 可保留单采样尾部，有限时长按原生音频节点语义裁剪 padding；25 ms 连续区间仍为经验容差。非 1x 继续按 `round(输入采样数/倍速)` 量化输出长度，单源采样在 >2x 时可量化为零，不能宣称全倍速保留全部源采样。 |
| HTTP 连接 5 s／阻塞读取 10 s、FCUP 10 s、资源 30 s／浏览器单元读取 15 s | 分别约束不同阶段。FCUP／浏览器截止及真实 JVM 响应头、初始体、返回流体的 10 s 读取到期已验证；Android 实际网络栈和 5 s 连接到期仍未验证。成功 FCUP 后复用当前资源路线，避免每个读取单元重复支付已失败 HTTP 的超时。 |
| 内联资源 2 MiB | 复用播放列表／元数据解码上限，同时限制编码和中间缓冲；123,248 字节的现场字幕远低于此值，应在本地解析。恰好上限、超限、Range 和无 FCUP 回退均由代理回归覆盖；不是已测得的 iPhone URL 大小上限。 |
| 镜像 NoData 输出等待 2000 ms | 只限制已提交真实 AAC 未输出、挡住后续静音的故障等待；连续静音不延长计时，不是额外播放缓冲。源采样队列按这段时间加既有 32 个输入块余量有界；会话退休立即取消，不影响新 epoch。 |
| FCUP 默认 16 个 pending、资源及请求体各 32 MiB | 第 16／17 个准入、共享不延长截止、10／30 s 前后 1 ns 均有默认参数回归。32 MiB 的解码资源与 `/action` 整体请求体属于不同数据域，均实测上限及 ±1 字节；plist 封装会占用请求体预算，不能相加成总内存上限。 |
| 投屏 demux cache 16 MiB | 是原始字节缓存的软淘汰阈值，实测可保留跨越阈值的一个 entry。产品 256 KiB 读取单元下，16 MiB＋256 KiB 仍命中，进一步增长触发首块淘汰；通用 vendor 接口若收到更大单块，超出量也可更大。不能当成 JS 堆／GPU 硬上限。 |

### 尚待补证与选值标定

MAD 3／0.5／1.5 ms 精确拒绝门槛、125 ms 计划历史长链、source 一秒桶与最快
到达点、device／source 2／10 s 配对边界已补独立回归；64／128／256 帧输出映射也已
验证，保留 128 帧保守下限并覆盖更大实际块，不依赖 Debug。真实 Soxr 验证到
1024 帧，混音缓冲不足时才扩容，避免固定 512 帧缓冲越界。
真实 JVM 套接字已分开验证 10 s 响应头、初始响应体和流式读取到期。剩余范围包括
Android 实际连接／读取到期、native 400 ms buffered anchor 与浏览器播放的现场关联，
不同车辆的实际 render quantum，以及无 worklet／原生块大小提示的 URL context。
beta.11 修复了输出延迟变化时错误重置已应用设备速率、初始加载指示空白和
借屏命令写入中的重入丢失；beta.10/v76 现场观察与这些后续修复分别记录。
beta.12/v78 的 255.671 s 采集仍不能证明爆音消除。同轨快照中的 CarPlay
clock-step 增量从 beta.11 的 188／730.046 s 变为 2／55.019 s；负载、源和触控
不同，不能量化可听改善。镜像源采样连续，但入站／发送尝试有 260／265 ms
空档；浏览器 renderer 仅早期增长不排除应用音频空档或物理输出问题。
用户确认 4K 投屏本身无法连续播放，不能用其 26 次／3.055517 s 调度空档解释
稳态爆音；两段 360p 零记录异常也不代表声学无错。20／10／40 ms 原生时间戳门槛、8／30 ms 恢复门槛、
live 余量／提前量／增长衰减和触控保持已补精确边界及突变核验；
URL 750／1500 ms、500 ms 提交和 2／3 s 前瞻也补独立边界。
水位需计入既有 2 ms 区间容差；前瞻允许最后整包跨界，不能称为内存硬上限。
原生 fake-clock 回归已补证 400 ms 余量仅加算一次，涵盖映射／fallback、暂停与退休；
这不能替代实际扬声器启动时间测量。

借屏新证据区分所有权与画面恢复：镜像归还后 2.007 s 触发缺流 fallback，
5.119 s 后实际绘制恢复；投屏两次获准借屏后 322／131 ms 收到 peer EOF，
后续为新 CarPlay 会话，iPhone 内部原因未知。
URL 的 500 ms 音频排程还受共同声画覆盖限制；beta.12 现场的 96 MiB 仅容纳约三幅 4K 画面。
旧 96 MiB 基线 oracle 在 180 ms 主线程停顿下重现约 115 ms 音频空档；持续慢视频
12 s 有 42 次空档。audio-master 可能造成无界视频落后，替代方案最终未采纳；
Worker、可用的低成本源及实际硬解吞吐和持续慢解码回归仍在
[Todo](Todo.md#ordinary-airplay)。URL 视频预算按用户要求改为 256 MiB；
CarPlay／镜像 64 MiB、32 个投屏排队画面及 URL 水位／500 ms／同步约束不变。
另外已复现直播音频的两处波形突变：恢复尾音重复施加淡出，以及语音切换时媒体
增益瞬间在 1／0.2 之间跳变。当前源码修复包络衔接并复用既有 5 ms 淡变，
覆盖 CarPlay 与镜像共享混音；不能据此宣称独立 URL 音频或全部实车爆音消除。
参考 LIVI 的 CarPlay 改进仍明确延期，本轮跳过；视频预算与这些音频修复分别验证。

已有运行证据的余量、提前量、增长／衰减、触控保持／追赶、水位／前瞻和容量
仍属于待标定默认值。需要同设备、多负载对照，比较延迟、停顿、恢复频率和
实际声音；不能用“按公式生效”代替“选值适合车辆”。数学导出的 1.875 曲线
系数与实现经验阈值应分别说明。

复测使用有界的拟合状态／噪声／接受年龄、实际 render quantum、native 锚点和
资源阶段耗时证据；缺失字段保留 unknown，不增加逐包日志来推算不可观测的
物理输出。可执行检查、标定项目和不生效配置清理集中在
[Todo 的参数证据清单](Todo.md#playback-parameter-evidence)，日志解释见
[Diagnostics](Diagnostics.md)。

beta.8 的有效非触控窗口中，部分 drops 不变的长间隔与源 PTS 空档吻合，
不能将静态按需更新直接认定为用户可见卡顿；另一些连续 PTS 的到达间隔
约 180–190 ms，目标缓冲虽提高，实际游标仍在收敛。本包没有触发旧锚点
过期，故不能以该独立修复替代本次归因。镜像可观测窗口很短，解码 P95
约 138–284 ms，目标已碰到 280 ms 上限，不能再凭空加大缓冲。
Debug 的同步写盘会影响观测，捕获完整也不证明没有性能干扰。完整日志
解释与输出测量限度见 [Diagnostics](Diagnostics.md)。
投屏 profile 中的 3000 ms、100 ms 余量和 readiness 衰减不控制 URL 引擎的
实际等待上限；不能把 3000 ms 当成启动耗时保证。URL 引擎实际使用水位、
前瞻时间和帧／字节容量。相关超时按各自阶段约束网络读取。

## 传输与资源约束

- `/rtc/pair/start` 与 `/rtc/pair/finish` 使用 SRP-6a 双向证明和会话密钥
  绑定完整 offer/answer SDP；四位码不在 HTTP 信令中传送。保留浏览器所有权与退役语义。
  `control`、`video`、`audio` 均 reliable ordered，不设部分可靠重传限制。
- 安卓依赖固定 `io.github.webrtc-sdk:android:150.7871.01`；已核查四 ABI、
  最低 API、实际 AAR 与许可证，见 [第三方说明](Third-party-notices.md)。
- 媒体只走直连 host ICE，无公共 STUN/TURN 或互联网媒体中转。分片最多
  16 KiB（含 24 字节头），保留传输 epoch、record sequence、完整长度和偏移；
  复用媒体记录中的原时间基、配置 epoch 和原序号。
- 应用层信用按完整记录消费返还；`bufferedAmount` 不作为远端消费证据。
  视频 16 MiB、音频 2 MiB 窗口，控制队列、解码准入、已解码面和等待时长均有界。
- 音频重新订阅带独立 generation 和首记录序号 barrier；跨通道乱序时先完成并
  丢弃旧在途记录，新 reader 不会重播旧指导音。已排队旧触控也不能借新会话发送。
- 完整压缩流保持解码依赖顺序。触控只跳过已解码旧画面；持续过载、信用停滞
  或解码无进展会记录原因并退役恢复，不通过暗丢预测帧或改 PTS 伪装达标。
- Android NetworkMonitor 对无 Network handle 的 AP/别名接口可能标为不可用；
  当前使用 native 接口枚举与真实套接字绑定，不通过改写 ICE 候选假装连通。
  `169.254.111.111/32` 的实际双向 UDP、选中候选与热点恢复仍需实车检查。
- 原始视频仅在安卓输入捕获一份。下游分片不再保存一份完整视频，音频保留
  自身格式/重置/路由语义；通话与麦克风仍走既有安卓 HFP/SCO。

## 诊断与已修复的遗留问题

日志区分建连阶段、候选数/UDP 类型、ICE/通道错误、重组错误、消费信用、
解码背压/停滞、已解码但未呈现与原始捕获完整性。故障快照即时上报，避免
自动重连先替换状态；Standard 保留故障与安全异常链，Debug 保留有界细节。
候选诊断不保存 IP、SDP 凭据或私有资源 URL；完整原始内容只随显式 Debug 捕获。

已修复：压缩队列拥塞静默丢帧、软件能力误广告、音频受视频计划牵引、
AirPlay 暂停破坏预测引用链、UDP 音频线程异常后悬挂、URL 旧请求回落到新
播放 owner、原始捕获重复打开文件及脱敏后故障整行丢失。捕获 writer 同步
flush；存储失败记录首末时间与来源，不能把 flush 当成断电耐久保证。
详见 [Diagnostics](Diagnostics.md)。

日志无法证明应用读取前的丢包、不可观测的硬解选择、GPU/面板扫描或真实
扬声器输出，也不能承诺解释所有理论上的硬件/系统错误。

## 配对与信任边界

HTTPS 页保护静态代码并提供安全上下文。四位码通过 SRP-6a 双向证明使用，
而不是在 HTTP 中发送；浏览器验证服务器证明及完整 SDP 的会话密钥 HMAC 后
才应用 answer，DTLS 指纹包含在该认证绑定中。Tesla 手工输入地址与四位码
即可，不需要剪贴板、长指纹或新的车端应用。单次 challenge、在线猜测锁定、
未认证 peer 与会话数量/超时限制仍然必要，不能把 PAKE 写成可防止拒绝服务。
AirPlay HTTP 资源的随机会话 bearer 从加密控制通道发放；HTTP 资源本身仍有
局域网机密性限制。SRP 验证后仍须在 DTLS 控制通道完成 `{k:'auth',q,s,c}`，才释放媒体和所有权。
随机资源 bearer 仅随认证成功的加密响应发放，不在 HTTP finish 暴露；
资源/bye 只用该 token。可信时钟样本来自认证 DC status，公开 `/hello` 不作
可信时间锚点。媒体与控制不回落到裸码 HTTP 路由。

### TCP 背压实测

[Debug TCP 接收探针](Diagnostics.md#debug-tcp-receive-backpressure-probe)
的持续运动测试结果：

| 阶段 | 安卓接收情况 | 到达时间减源计划呈现时间 |
| --- | --- | --- |
| 无限制基线 | 约 11–12 Mbps、60 fps | 通常约 −60 至 −70 ms |
| 70% 读取预算 | 约 7.2 Mbps | 增长到约 4.5 s |
| 40% 读取预算 | 约 4.1 Mbps，帧率进一步降低 | 最大约 8.18 s |
| 恢复无限制 | 短时约 41.32 Mbps、107 fps，随后回到基线 | 快速回到约 −66 ms |

读取限速生效但产生明显积压；吞吐下降不等于源编码降码率。源端是否减少
生成或丢弃帧仍未确定。负偏差表示相对计划呈现时间提前，不是负采集延迟。

现有浏览器会丢弃超过呈现期限的帧并保留上一幅 Canvas 画面，秒级积压与
冻结观察相符；缺少该次浏览器计数，冻结位置尚未确认。DataChannel
不沿用此压缩帧丢弃策略；可靠路径保留完整压缩接收与依赖解码。
不通过数秒播放窗口掩盖积压；缩小接收缓冲区也只能作为独立实验。
