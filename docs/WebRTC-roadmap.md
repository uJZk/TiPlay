# WebRTC 实施路线图

## 当前决策与下一步

产品实施路线遵循 [CarPlay 可靠有序 DataChannel 交接契约](CarPlay-DataChannel.md)：
安卓传递完整压缩媒体，车端网页控制硬件解码和 Canvas 输出，音频保持独立时间线。
本页维护实车实验的证据、实现进度及后续验收；具体协议、时延及资源要求以该契约为准。
`feat/carplay-webrtc` 已接入可靠有序 DataChannel，形成 `0.2.21-beta.3` 测试版。
测试网页位于 <https://ujzk.github.io/TiPlay/webrtc/>，测试 APK 默认选择该地址；
现有站点根目录和下载页继续使用迁移前基线，正式用户的 HTTP 路径不被替换。
网页实际硬件解码是明确要求，尚无本次实车硬件使用的验收证据。

**用户已确认 beta.2 / v70 的真实 CarPlay 可以播放。**
2026-10-20 的日志覆盖 HEVC → WebCodecs Worker → Canvas，包含三个源画面段；
浏览器摘要未见压缩帧序号缺口、解码错误或 RTC 重连。原始采集约 72 秒，
不能代替长时间、换挡、实际硬件解码或物理输出验收。

此前的 D 是同一车浏览器内的本机 WebRTC 接收视频轨
→ MediaStreamTrackProcessor → VideoFrame → Canvas 合成源测试。它已经有
实车可播放的用户观察，不能再把此前笼统的“P 档视频不能播放”套用到 D。

尚未收到明确的 P → 非 P → P 连续播放结果、车辆固件和实际解码硬件证据。
本次没有完整保存选中 ICE 对统计，因此不能将已连通直接称为 UDP 路径验收。

**下一验收重点：补齐源出帧及解码后丢帧的分项证据，定位持续运动时的停顿。**
支持的测试地址包括
`169.254.111.111` 和 Shizuku/Root 下的 `100.111.111.111`。
beta.2 已有跨设备播放反馈，仍须补齐所选候选、长期可靠性、
换挡持续播放及网页实际硬件解码。D 的结果不更改已选产品传输方案。

## 约束摘要

- 只覆盖安卓手机 + 车浏览器，不包含原生车机。
- 永不二次编码。允许解密、配置解析、访问单元整理及传输封装，保留源压缩视频。
- 媒体只走局域网，不引入公网或 TURN 中转。GitHub Pages 可托管 HTTPS 静态页，
  但静态托管不等于信令或安卓可达；配对须绑定真实设备、会话和 DTLS 指纹。
- 采用可靠有序 DataChannel，不配置 `maxRetransmits` 或 `maxPacketLifeTime`。
  完整压缩接收和依赖解码继续；触控追赶允许跳过已解码旧画面。
- 视频、音频各自相对源呈现时间不超过 +300 ms，通常尽量低；不是固定缓冲目标。
  触控只追赶视频，不重置、加速或改变音频时间线。详见交接契约的测量边界。
- 回声、麦克风和通话继续走既有安卓 HFP/SCO，不另建浏览器采麦或 AEC 方案。
- 保留现有配对、浏览器会话所有权、触控及独立音频语义；车端不依赖复制粘贴。
- 完整原始视频只保存一份，下游事件引用原记录；不静默采样或遗漏原始码流。

## 当前证据与边界

| 项目 | 当前观察 | 尚未证明 |
| --- | --- | --- |
| D 本机 WebRTC → Processor → Canvas | 用户明确反馈“D 可以” | 跨设备网络、换挡持续播放、实际硬件解码、真实 CarPlay 通过 |
| 其他播放路径 | 此前反馈“P 档是视频不能播放”，未明确指向 B/C；D 现已单独确认为可播放 | B、C 的具体失败原因和档位对照 |
| 手机到车端连接 | beta.2 / v70 已确认真实 CarPlay 播放，三个源画面段切换后继续，摘要重连/序号缺口/解码错误均零 | 选中候选及协议、长期稳定性和换挡连续性 |
| 本地权限弹窗 | 用户未看到弹窗 | 不能单凭这一点判断权限；接收视频本身不要求摄像头或麦克风授权 |
| 热点地址 | 用户用 Shizuku；地址改为 `100.111.111.111` 后，beta.2 的内核网卡枚举版本已可播放 | 未做只改变一个变量的地址/枚举对照，不能单独认定某地址类别或监控模式是根因 |
| 本次丢帧 | 首段至少 88 次、末段截至末次摘要 15 次，合计已知至少 103；末段源 PTS 最大间隔约 1.27 秒 | 静止内容减帧与运动时源停顿的区别；调度/绘制/刷新替换的具体占比 |
| ICE 地址别名实验 | 额外公布附加地址候选，保留原候选及 UDP 端口 | 候选生成不会创建或重新绑定套接字，尚无该地址实车双向连通证据 |
| TCP 接收背压 | 持续运动测试中呈现偏差增长，用户同时报告网页冻结 | 源编码码率是否适应仍未确定；当前读取限速不作为默认拥塞闭环 |

Shizuku 在热点接口添加真实 `/32` 地址，见 [热点地址说明](Hotspot-address.md)。
页面可筛选或交换候选，不能强制浏览器绑定指定网卡。实际 UDP 端点须能
在该地址接收和回包；单向到达也不足以通过 ICE。

测试版的浏览器专用安卓 WebRTC 工厂改用内核网卡枚举，避免默认
Android NetworkMonitor 忽略没有 ConnectivityManager Network 的热点接口。
它不按 169.254 地址类别过滤，也不伪造 SDP 候选。关闭该监控会失去按
Android Network handle 绑定套接字和网络变化通知，实际出入路径仍由系统路由、
UID/VPN 规则决定；当前已有实车播放，候选对照和网络切换结果仍待验证。

beta.3 补齐独立 Debug 视频快照与源帧节奏摘要，按源画面段及采集会话关联。
普通摘要之外保留丢帧分项、区间基线、完整帧到达/源 PTS 间隔以及传输阶段指标；
这些是观测改动，不放宽时延期限、不增加缓冲，也不重编码。

### TCP 背压实测

[Debug TCP 接收探针](Diagnostics.md#debug-tcp-receive-backpressure-probe)
的持续运动测试结果：

| 阶段 | 安卓接收情况 | 到达时间减源计划呈现时间 |
| --- | --- | --- |
| 无限制基线 | 约 11–12 Mbps、60 fps | 通常约 −60 至 −70 ms |
| 70% 读取预算 | 约 7.2 Mbps | 增长到约 4.5 s |
| 40% 读取预算 | 约 4.1 Mbps，帧率进一步降低 | 最大约 8.18 s |
| 恢复无限制 | 短时约 41.32 Mbps、107 fps，随后回到基线 | 快速回到约 −66 ms |

读取限速生效但产生明显积压；吞吐下降不等于源编码降码率。源端是否减少
生成或丢弃帧仍未确定。负偏差表示相对计划呈现时间提前，不是负采集延迟。

此次测试所用的原 HTTP 浏览器会丢弃超过呈现期限的帧并保留上一幅 Canvas 画面，
秒级积压与冻结观察相符；缺少该次浏览器计数，冻结位置尚未确认。测试版
DataChannel 对压缩队列超载/超时明确结束并恢复会话，避免隐瞒压缩数据缺口后继续
播放；仅允许跳过已解码的旧画面。这些策略仍须验证真实网络与解码负载。
不通过数秒播放窗口掩盖积压；缩小接收缓冲区也只能作为独立实验。

## 阶段 0：补齐车端播放证据

[车端单机测试页](https://tiplay-webrtc-probe.sunlitbloom10.chatgpt.site/gear.html)
排除了手机配对和跨设备网络依赖，四项分别观察：

| 项目 | 观察内容 | 状态 |
| --- | --- | --- |
| A：纯 Canvas 动画 | 页面计时和绘制；不证明视频能力 | 仅作对照 |
| B：普通 H.264 `video` | P 档起播、暂停和换挡行为 | 待明确单项结果 |
| C：H.264 WebCodecs → Canvas | 送入、解码、绘制计数和实际硬件使用 | 待明确单项结果及硬件证据 |
| D：本机 WebRTC → Processor → Canvas | 本机 ICE、接收视频轨与绘制 | 用户确认可播放；换挡对照及运行配置待补 |

B 的短片先下载到 Blob，C 使用同源 H.264 数据。D 使用同页两个
PeerConnection，属于真正的本机视频轨测试，不是手机到车端的网络测试。
页面不自动恢复暂停，也不读取车辆档位。

记录浏览器/车辆固件、页面版本、编码、处理路径和统计。按同一路径比较
P → 非 P → P 的画面及计数，区分页面、网络、解码与绘制停止。D 成功不能
替代 C 的硬件解码证明；`prefer-hardware`、低 CPU 或配置成功也不能单独证明。

## 阶段 1：认证信令已实现，真实 UDP/ICE 待验

1. 在运行 TiPlay 的同一台安卓手机上确认热点及 Shizuku 附加地址有效。
   [浏览器配对实验页](https://tiplay-webrtc-probe.sunlitbloom10.chatgpt.site/)
   的 Cloudflare 信令只用于实验，不属于产品纯局域网信令。
2. 对照原候选和别名实验，记录所选候选对、协议、双向收发及恢复。
   如浏览器套接字不能复用附加地址，改用安卓原生 UDP/ICE 最小探针，
   验证真实绑定、回包源地址、库的链路本地地址枚举及端口控制能力。
3. 测试版已通过 `/rtc/pair/start`、`/rtc/pair/finish` 实现四位码 SRP-6a 配对，
   完整 offer/answer SDP 与会话绑定经相互证明和 HMAC 验证后才使用 DTLS 身份；
   验证向量和篡改测试覆盖协议实现。车端手输地址和四位码，不依赖复制粘贴。
   已接入代码失效、接管、断开、超时和旧 epoch 退役；这些机制的实车交互仍待验。
   HTTPS 页或 DTLS 加密本身不代替配对身份绑定。
4. 验证热点重启、地址重加和重连。通过条件是实际地址上的双向 ICE 连通，
   不是 HTTP 成功、信令成功、候选已添加或手机本地动画。

## 阶段 2：可靠有序 DataChannel 已实现，跨设备服务能力待验

[产品协议与资源边界](CarPlay-DataChannel.md#native-and-browser-transport) 已实现：
安卓固定 `io.github.webrtc-sdk:android:150.7871.01`，包含四种 ABI，并记录许可证、
来源、线程和生命周期处理。三个可靠有序通道分别承载视频、音频与控制，不使用
原生音视频轨，不设置部分可靠性参数，也不引入公网 STUN/TURN 或媒体中转。

源记录保留原线格式、epoch、序号与时间信息，在最多 16 KiB 的完整消息内分片，
再由网页按有序通道完整重组；协商的 SCTP 上限进一步限制片段。会话身份、
长度、偏移和连续性均检查后再分配/消费。应用层信用和累计完整记录确认配合
`bufferedAmount` 限制在途工作；后者不能证明远端消费、解码或呈现。

媒体与控制保持逻辑分离，但多个通道共享 SCTP 关联和拥塞资源。安卓视频和音频
可靠队列都限定 200 ms 最老媒体年龄，并分别限制字节数、帧/记录数；超载、
超时或长时间消费停滞明确结束会话，不丢压缩预测帧后继续，也不无界排队。
完整 AU、重组、信用、异常长度及队列失败已有软件测试；实际热点上的大 IDR、
丢包重传、控制响应、持续吞吐与热负载仍须用真实 iPhone/安卓/车端测量。

原始视频仍只保存一份源 TCP 采集，下游通过会话、记录 ID 和字节范围关联，
明确解密及 Annex-B 整理过程；写盘失败暴露完整性边界，不宣称未知范围已保存。
D 使用的原生视频轨保留为实验结果，不替换产品的源压缩 DataChannel 路线。

## 阶段 3：时钟、独立音频与触控追赶已接入，物理输出待验

`ScreenCodec.senderNanos` 读取源呈现时间，`NtpClock` 在同步有效时映射到安卓
单调时钟；测试版复用该映射并通过控制通道校准安卓与浏览器时钟。源锚点缺失时
明确报告本地/到达时刻测量边界，不把首帧到达当作源呈现零点或宣称满足
源相对时延。计时映射和软件提交指标不能替代实际面板与声学输出测量。

AAC、Opus、LPCM 保留源格式和独立语义，由网页独立解码/输出，不为适配
WebRTC 二次编码。触控接入独立控制通道，视频以连续游标平滑选择已解码图像
追赶，音频保持原时间线。初始追赶参数为最高 1.5 倍、速度变化率 4/s；
重复触控保持连续，松手不恢复旧积压。这些是测试参数，不是实车平滑性证明。
解码准入保留必要预测前视，并限制待解码工作与已解码图像；不能只允许一个
压缩 AU 等待输出而造成依赖死锁。实际硬件内部队列及编解码配置仍需实测。

WebRTC 反馈影响安卓调度，不会自动改变 iPhone 编码器。现有接入层有请求
关键帧操作，未确认运行时源码率控制命令。持续超载无法同时保证完整输入、
有限资源和时延上限；须报告违约并走真实支持的协商/恢复边界，不能通过
暗丢压缩预测帧、重置 PTS 或无界积压使指标看似通过。

## 阶段 4：真实 CarPlay 验收与切换

比较真实 iPhone → 安卓 → 特斯拉的基线与候选方案，验证网页硬件解码、
独立源相对 +300 ms 音视频上限、触控平滑追赶和一份完整原始视频记录。
覆盖大 AU、重传、持续运动、热负载、档位切换、后台恢复、热点重启、
浏览器接管、存储压力及 HFP/SCO 路由；物理显示和声学时延须有独立测量。

D 的单机可播放已作为前置证据记录；DataChannel、认证配对、媒体与触控的软件
实现已接入测试版。跨设备真实 ICE、源压缩媒体在车端实际硬解、真实 CarPlay、
档位切换及端到端物理输出验收仍未完成。测试版部署在独立 `/webrtc/` 路径，
正式站点根目录保持迁移前行为；只有实车验收通过后才决定正式默认传输切换。
