# TiPlay libsoxr: JavaScript and Android engineering report

Final artifact SHA-256: `0dda221ebb9979a01840c475caed3d9aee84c436f4a1e91483a868ca5df85777` (364339 bytes). Pinned upstream: chirlu/soxr `945b592b70470e29f917f4de89b4281fbbd540c0`.

The performance result is a tradeoff: five rotating fresh-process runs show 44.1→48 kHz stereo CPU about 10% lower than the unoptimized JS baseline, while 48→48 kHz stereo CPU is about 5.2% higher. The WASM reference remains substantially faster. The final implementation satisfies the explicit pure-JavaScript requirement and measured signal equivalence; it does not establish a universal CPU improvement or guaranteed real-time deadlines.


The final file is standalone static typed JavaScript generated by wasm2js, **not validated legacy asm.js**. It needs neither runtime WebAssembly nor dynamic JavaScript compilation. Intermediate WASM is used only offline by the compiler. The generated asset is 28.6% smaller than the original unoptimized JavaScript translation (510242 bytes); original WASM was 69343 bytes and is restored from checksummed Git history into `work/` only as a benchmark reference.

## Scope and accepted review changes

A coordinating subagent cloned the pinned upstream into a temporary work directory, then commissioned two independent child agents. DSP review required retaining every vr32 filter, half-band stage, phase clock and ratio-transition crossfade; the final source keeps those intact and specializes only float32 IO, including mono memcpy and stereo deinterleave/interleave. Unreachable int16/int32/float64 conversion/dither branches were removed from this export boundary. Source includes the original copyright and LGPL notices, the exact patch, complete upstream archive, and GPL TiPlay wrapper/glue.

Runtime review required static ESM with no eval/Function, a fixed heap, identical wrappers for engine comparisons, real CSP AudioWorklet loading, and separate CPU versus elapsed-block timing. All were adopted. Following the initial review and measurements, three rotating repetitions compared a second optimization that disabled wasm2js `-O3` while retaining clang `-O3 -flto` and wasm-opt `-O3`. It reduced core-case CPU by roughly 3–5% and mean block time by 6–10% relative to the smaller first candidate. The final build uses that measured selection; neither the `-O3` name nor source size was treated as a speed guarantee. `../../tests/bench/soxr/initial/variant-summary.json` and raw runs preserve that decision. No fast-math, filter-quality change or audio-latency limit relaxation was used.

The JavaScript factory initializes synchronously and returns the existing C-style TiPlay ABI. The production adapter can cache heap views because memory is fixed at 16 MiB. Formal engine measurements retain the same original wrapper for all three backends, so they do not attribute separate production wrapper improvements to the DSP engine.

## DSP and timing correctness

Independent DSP results are `../../tests/bench/soxr/candidate-final.json`:

- 28 representative combinations: 8/16/24/32/44.1/48/96 kHz input, 44.1/48 kHz output, mono/stereo. The protocol accepts 8–96 kHz; preserving libsoxr's general variable ratio supports the negotiated range, although every integer rate was not individually enumerated.
- Continuous versus irregular 137-frame input packets produce identical static-ratio samples. Stereo silence stays isolated. Final JS matches original WASM samples exactly for all measured cases; no nonfinite samples.
- ±4.9% ratio ramps preserve output-frame slew, continuous filter state and transitions through 1:1. Cross-packet dynamic scheduling error is at most 1.61e-6 amplitude (the same upstream rounding behavior), while candidate versus reference error is zero.
- Three antialias probes match the reference: 96→48k at 36kHz = −128.15 dB; 48→44.1k at 23.5kHz = −116.04 dB; 96→44.1k at 36kHz = −128.15 dB. These are selected probe results, not a comprehensive THD+N or complete frequency-response certification. Exact measured sample equivalence protects against distortion regressions on those inputs.
- Fourteen impulse-energy-centroid calibrations match exactly (−0.01134 to +0.16440 ms relative to ideal resampled impulse location). Slightly negative sub-sample centroids are numerical/filter-phase offsets, not negative causal latency. They are not network startup or speaker latency. Upstream vr32 delay reporting is incomplete, so the existing energy-centroid calibration remains in use.
- 120 seconds of simulated continuous drift emits 5760000 output frames. Two independent engines consume exactly 5292252 input frames with zero sample difference; the final queued input lead is 245.83 frames. This verifies state/clock continuity and matches the reference, rather than claiming zero queue depth or zero real-world clock drift.

No CarPlay 0 ms, mirror 200 ms, or early 45 / late 125 ms policy was changed to obtain these results. Packet reordering, epoch resets and video scheduling belong to the existing timeline/integration tests, not this DSP microbenchmark.

## Formal performance measurements

All engines use the same pinned original StreamingResampler adapter, 128-frame drain-before-feed blocks, rate slew schedule, deterministic input and 16 MiB starting heap. A 28-format matrix measures 4000 steady blocks after 500 warmup blocks per case. The core matrix additionally uses five fresh processes per engine with rotating engine order (20000 steady blocks per core case/engine). Node v24.19.0 / V8 13.6.233.17, Linux x86_64, Intel Xeon Platinum 8573C, five visible CPUs (the cgroup CPU quota permits four CPU-seconds per second). These are shared-host observations. Engine initialization and stream construction are excluded from steady block timings and separately recorded in raw JSON.

## Runtime and memory

A real Chromium 151.0.7922.173 AudioWorklet loads the final asset with production `script-src 'self'`, while its WebAssembly global is explicitly disabled. It emits all 25600 frames over 200 render quanta with zero errors, nonfinite samples or CSP violations. See `../../tests/bench/soxr/Final-strict-csp.json`. This confirms actual browser/worklet/CSP compatibility; it is a short smoke test, not a full duration car test.

Each factory uses 16777216 bytes of fixed heap. Two simultaneous media/navigation streams and 1000 create/delete cycles complete without heap growth or allocation failure. Native FIFO operations may still realloc/memmove within the heap; the original wrapper also allocates JavaScript views/results. We do not claim a zero-allocation render path, exact allocator live/high-water usage or proven leak absence. Those counters are not exposed by this ABI. Process RSS/heapUsed measurements include V8/JIT and are retained as auxiliary observations.

## Reproducibility and limits

The final recipe was executed from a fresh temporary extracted source directory and reproduced the exact shipped SHA-256. Pinned source checksum, compiler/Binaryen URLs and checksums, source patch, static glue and licenses are supplied. [rebuild record](../../tests/bench/soxr/Rebuild.txt) records the final rebuild. Follow the [vendor README](../../site/play/vendor/soxr/README.md) to regenerate using verified toolchains.

Desktop x86_64 Node and Chromium results do not establish performance on Android ARM/old car browsers, especially engines without modern JIT or with throttling. AudioWorklet has a shared render deadline (2.667 ms per 128 frames at 48k), including timeline/mixing/copies; isolated DSP timing cannot certify that whole deadline. Shared-host OS scheduling produced long outliers even for the WASM reference. Detailed CPU timing is measured in Node because AudioWorkletGlobalScope does not guarantee performance.now(). The real browser test demonstrates compatibility, not per-block CPU percentiles. No real car, complete ten-minute hardware drift test, or video smoothness improvement is claimed.

## Android C/JNI reuse

Android SCO playback and capture compile the same pinned, float32-patched vr32/HQ
C engine directly with the NDK. The checked-in subset is reproduced by
`prepare-native.py --check`; each stream owns a native handle. It has no JavaScript
or WASM runtime. The old Kotlin FIR/linear converter is removed. Android's output
device still has its own clock; this does not port the browser's AudioContext API.

`scripts/test_soxr_native.py` compiles actual host JNI and runs the Gradle-compiled
Kotlin adapter/mixer. It checks six rate pairs, exact split/whole-packet parity,
continuous duration without flushing temporary shortages, impulse content offsets,
alias rejection, ratio calls, independent concurrent handles, invalid/closed-handle
rejection, PCM bounds and native lookahead deadline preservation. The raw result is
[Native-jni.txt](../../tests/bench/soxr/Native-jni.txt). Impulse content offsets are
not startup latency: the unflushed variable-rate filter retains input lookahead.

The surrounding speech queue measures PCM frames, AAC's 1024-frame units and Opus
TOC/frame counts. Both summed duration and RTP span are bounded to 160 ms, with a
secondary memory safety cap. Original arrival/presentation leases survive codec
waiting; stale decoder output cannot borrow a fresh packet's timestamp. PCM carries
per-frame deadlines corrected for resampler lookahead, and rendering accounts for
AudioTrack frames already queued. Source gaps, trimming, expiry and underrun use
5 ms in-place recovery; stream retirement is immediate. Tests separately exercise
the signal envelope, a blocked shadow MediaCodec, timestamp wrap, variable packet
lengths, output queue lead and expiry isolation. See [Testing](../../docs/Testing.md#native-sco-resampling-and-continuity).

These checks establish host DSP and software timing behavior. Four-ABI APK assembly
does not prove physical Android native loading, Bluetooth acoustic quality,
speaker latency or sustained device-clock drift; those remain device acceptance.
